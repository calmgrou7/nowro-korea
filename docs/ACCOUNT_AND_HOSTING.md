# 계정 로그인 및 상시 배포 준비 — 2026-10-06

## 이번 단계의 범위
### 현재 로그인 방식

2026-10-07 NOWRO 관리자 로그인 후, 현재 프로젝트의 기본 발송 서비스에서 메일 본문 편집이 별도 SMTP 또는 Pro 요금제를 요구하는 것을 화면에서 확인했다. 요금제나 SMTP를 변경하지 않고 **기본 가입 확인·로그인 메일의 버튼 방식**을 연결했다. 아래 인증번호 템플릿 안내는 향후 메일 편집을 활성화했을 때의 선택 사항이다.

- Supabase Site URL을 `https://promised-obvious-correctly-semi.trycloudflare.com/`로 저장하고 새로고침 후 유지되는 것을 확인했다. 추가 Redirect URL이나 와일드카드는 등록하지 않았다.
- 서버 `.env`의 `PUBLIC_APP_URL`도 같은 주소로 설정했다. 로그인 요청에서 이 주소만 사용하며 브라우저가 보낸 Host나 이동 URL을 신뢰하지 않는다.
- 메일 링크의 인증 토큰은 URL fragment에서 읽은 즉시 주소창에서 제거한다. 브라우저 저장소에 저장하지 않고 서버에 전송한다.
- 링크를 열면 서버에서 검증한 이메일을 보여주고 **사용자가 본인 계정임을 확인한 뒤** 로컬 로그인 쿠키를 교체한다. 미리보기만으로 회원 기록을 합치거나 로그인하지 않는다.
- 서버는 access token과 refresh token 양쪽의 사용자 일치를 검증하고 기존 계정과 다른 계정으로 바꾸는 요청을 거절한다. 인증 토큰은 기존과 같이 서버 DB에 암호화해 저장한다.
- 실제 새 메일 버튼 클릭→계정 확인→로그인 완료는 사용자 시험이 남아 있다. 이미 발송된 localhost 링크는 새 설정으로 바뀌지 않는다.
- 임시 터널 주소가 바뀌면 Supabase Site URL과 PUBLIC_APP_URL도 함께 바꿔야 한다. 고정 배포 주소가 마련되면 두 설정을 고정 주소로 변경한다.

Supabase 이메일 OTP 인증을 서버에서 검증하고 SQLite의 사용자 ID와 연결한다. 코스·쿠폰·스탬프·보상 기록은 아직 SQLite에 있다. Supabase 데이터베이스·Storage 전환을 완료한 구현이 아니며 기존 준비 스키마를 원격 DB에 적용하지 않았다.

인증 서버 설정이 없으면 로그인 준비 중 안내만 표시한다. 설정 후 이메일 → 인증번호 → 로그인 순으로 이용한다. 한국 전화번호와 비밀번호를 요구하지 않는다.

## 계정 설정
1. NOWRO 전용 Supabase 프로젝트를 생성한다. 기존 다른 서비스 프로젝트를 재사용하지 않는다.
2. 프로젝트 URL과 publishable key를 로컬 `.env`의 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`에 입력한다. 비밀키·DB 비밀번호·service_role 키를 채팅 또는 프런트엔드에 넣지 않는다. 이 인증 구현은 service_role 키를 요구하지 않는다.
3. Authentication의 Email 인증을 활성화하고 Confirm signup 및 Magic Link 이메일 템플릿 두 곳에 `{{ .Token }}` 인증번호를 포함한다. 첫 가입과 기존 회원 로그인에 서로 다른 템플릿이 사용되므로 두 곳 모두 설정한다. 기본 링크 템플릿만 유지하면 앱의 인증번호 입력 방식과 맞지 않는다.
4. 운영 발송량에 맞는 이메일 SMTP 설정과 인증메일 언어를 준비한다. 테스트에서는 본인 이메일로 송신·확인한다.
5. 서버를 재시작하고 설정 → 내 계정에서 실제 이메일 송신·인증·로그아웃·다른 기기 재로그인을 검증한다.

### 메일은 오는데 로그인 버튼이 열리지 않을 때

현재 앱은 이메일 링크 클릭 방식이 아니라 인증번호 입력 방식이다. 사용자가 받은 신규 가입 확인 메일의 `redirect_to`가 `http://localhost:3000`인 것을 확인했다. 해당 주소는 메일을 연 기기 자신을 가리키므로 외부 사용자가 나우로로 이동할 수 없다. 제공된 인증 토큰 링크는 열거나 저장하지 않았다.

1. 지정한 프로젝트의 Authentication → Email Templates(또는 Emails) → Confirm signup을 열고, 이어서 Magic Link도 수정한다.
2. Confirm signup에는 [가입 확인 인증번호 템플릿](../supabase/templates/confirm-signup-otp.html), Magic Link에는 [로그인 인증번호 템플릿](../supabase/templates/magic-link-otp.html)의 HTML을 본문에 적용한다. 핵심 변수는 `{{ .Token }}`이며 제목 예시는 `NOWRO sign-in code / 로그인 인증번호`다.
3. 저장 후 나우로에서 새 인증번호를 요청한다. 이미 발송된 메일의 내용은 바뀌지 않는다. 발송 제한에 걸리면 잠시 기다린 뒤 다시 요청한다.
4. 새 메일의 인증번호를 나우로 설정 화면에 입력한다. 메일 링크·인증번호를 채팅에 전달할 필요가 없다.

이메일 템플릿은 로컬 파일로 준비했으며 원격 Supabase 관리자에 적용하지 않았다. 이후 브라우저에서 사용자 관리자 로그인을 완료했지만 기본 이메일 서비스의 템플릿 편집 제한이 확인되어, 현재는 위의 기본 이메일 버튼 방식을 사용한다. 준비한 두 인증번호 템플릿을 적용하려면 별도 SMTP 또는 해당 편집을 허용하는 요금제를 연결해야 한다.

공식 안내: https://supabase.com/docs/guides/auth/auth-email-passwordless

## 인증·기록 처리
- 인증 응답을 서버의 `getUser`로 검증. 클라이언트 role 입력 및 user_metadata는 권한 판단에 사용하지 않는다.
- 이메일 발송은 주소당 60초 1회, 코드 검증은 주소당 10분 10회 제한. 인증 서버 자체의 정책도 적용.
- 로그인 시 로컬 HttpOnly 쿠키를 교체하고, 인증 access/refresh token은 서버 DB에 AES-GCM 암호화하여 보관. 토큰과 키는 프런트엔드에 반환하지 않는다.
- 인증 세션은 서버에서 사용자 검증·갱신. 로그아웃은 현재 앱 세션을 즉시 폐기. 인증 쿠키의 기본 유효기간은 7일이며, 만료 후 이메일로 다시 로그인한다.
- 인증 서버 연결 장애·5xx·타임아웃은 503으로 접근을 중단하되 기존 로그인 쿠키와 암호화 토큰을 지우지 않는다. 연결 복구 후 동일 세션으로 재검증한다. 실제 세션 만료·계정 검증 거절은 비회원 세션으로 전환한다.
- 비회원 기록을 계정에 이관. 중복 쿠폰은 사용 완료 상태를 우선 유지. 두 기록에 같은 캠페인 보상 신청이 있으면 자동 삭제·이중 수령 대신 충돌 안내 후 운영자 확인.
- 이전 결제 미검증 스탬프와 새 결제 완료 스탬프가 겹쳐도 결제 증명을 유지한다. 소비된 결제 기록도 유지해 같은 결제의 재사용을 막는다.
- 기존 회원 기록은 비회원 7일 정리 작업에서 삭제하지 않는다. 회원 탈퇴·보존/삭제 정책·실제 개인정보 문서는 출시 전 연결해야 한다.
- 상점과 관리자 역할은 기존 서버 users 테이블의 승인된 역할만 사용. 실제 업체 소유권 확인·역할 부여 화면은 후속 작업.

## 고정 주소 배포
`render.yaml`은 Render Web Service + 영구 디스크 배포 구성이다. **Starter 유료 서버와 디스크 비용이 발생하므로 계정 소유자가 요금제를 확인하고 생성해야 한다.** 현재 실제 Render 서비스나 고정 URL을 생성하지 않았다.

1. NOWRO만 포함한 Git 저장소에 코드를 보관한다. `.env`, `.data`, 인증 토큰·배송 정보·로컬 사진 원본 DB는 업로드하지 않는다.
2. Render에서 해당 저장소의 Blueprint를 선택한다. 다른 작업 폴더 전체를 저장소에 업로드하지 않는다.
3. Supabase URL과 publishable key를 서비스 환경변수에 입력한다. 서비스 역할 비밀키는 필요 없다.
4. 영구 디스크 `/var/data/nowro`와 `DATA_DIR` 경로가 일치하는지 확인한다.
5. 생성된 고정 `onrender.com` 주소에서 HTTPS, `/api/health`, 로그인, 기록 유지, 재배포 후 DB 유지와 모바일 접속을 확인한다.
6. 원하는 도메인을 연결한다. 도메인 구매·DNS 변경은 실제 계정과 도메인이 정해진 뒤 수행한다.

`DEPLOYMENT_MODE=public-demo`에서는 외부 바인딩을 허용하되 운영자 테스트 역할을 비활성화해야 한다. 이 배포는 샘플 안내가 유지되는 미리보기이며 결제·배송·실제 데이터 검증이 완료된 정식 출시가 아니다.

SQLite 영구 디스크는 단일 서버 초기 배포를 위한 중간 구성이다. 별도 백업·복구 검증이 필요하며 서버 여러 대로 확대하려면 운영 DB 어댑터 전환이 필요하다. `supabase/schema.sql`에는 이후 추가된 등록·결제·배송 데이터까지 통합하는 전환 작업이 남아 있다.

2026-10-07 현재 백업·검증·새 파일 복구 도구를 추가했다. 실행 방법과 운영 전환 주의사항은 [DATABASE_BACKUPS.md](DATABASE_BACKUPS.md)를 따른다. 사용자가 지정한 Supabase 프로젝트 URL과 publishable key를 `.env`에 반영했다. 인증 설정 조회가 HTTP 200으로 성공했고 이메일 로그인 활성화·가입 허용·이메일 확인 필요 상태를 확인했다. 공개 서버를 재시작하여 `authConfigured=true`, `operatorPreview=false`, `dataBackend=sqlite`를 확인했다. 실제 이메일 송신·OTP 템플릿·코드 검증·다른 기기 로그인 시험은 아직 남아 있다. 연결된 관리 계정은 해당 프로젝트 접근 권한이 없어 관리자 설정 변경은 수행하지 않았다.
